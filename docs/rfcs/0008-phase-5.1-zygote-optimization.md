# RFC-0008: Phase 5.1 - Zygote 10ms Optimization

**Status**: Draft
**Created**: 2026-01-03
**Target**: Reduce Zygote warm start from 43ms to ≤15ms (Bun parity: 10ms)

---

## 1. Executive Summary

Phase 5.0 achieved 14x speedup with Zygote preload (606ms → 43ms). However, Bun achieves 10ms cold starts. This RFC targets eliminating the remaining 30ms gap.

### Performance Gap Analysis

| Component | Current | Target |
|-----------|---------|--------|
| Rust CLI startup | ~10ms | ~5ms |
| IPC overhead | ~1ms | ~1ms |
| fork() | ~0.7ms | ~0.7ms |
| **Worker stdout wait** | **~30ms** | **~0ms** |
| **Total** | **~43ms** | **~15ms** |

---

## 2. Problem Analysis

### 2.1 Current Flow

```
CLI → IPC → Zygote → fork() → Worker executes → stdout → CLI reads → done
                                                    ↑
                                               30ms wait
```

### 2.2 Root Cause

The CLI **synchronously waits** for:
1. Worker process to complete
2. stdout to be flushed and read back

This blocking wait adds ~30ms overhead.

---

## 3. Proposed Solutions

### 3.1 Async Fire-and-Forget Mode (Primary)

For scripts that don't need stdout capture:

```bash
velo run --zygote --async script.py
```

| Change | Description |
|--------|-------------|
| CLI returns immediately after fork | No wait for stdout |
| Worker runs in background | Stdout goes to file/null |
| **Mutual Exclusion** | `--async` and `--profile` are mutually exclusive |
| **Fork ACK** | Zygote sends `Fork-Accepted` ACK before CLI exits |
| **Orphan Management** | Worker self-kills if orphaned (parent PID change) and TTL expires |
| Expected time | **~12ms** |

### 3.2 Pre-forked Worker Pool (Secondary)

Pre-allocate N workers ready to execute:

```python
# Zygote maintains a pool of pre-forked workers
worker_pool = [fork() for _ in range(N)]

# On request, claim a worker instead of fork
worker = worker_pool.pop()
```

| Benefit | Impact |
|---------|--------|
| Skip fork() latency | Save 0.7ms |
| Instant dispatch | Predictable latency |

### 3.3 CLI Startup Optimization (Tertiary)

| Optimization | Potential |
|--------------|-----------|
| Static linking | -2ms |
| Lazy CLI parsing | -3ms |
| Precompiled config | -2ms |

### 3.4 Configurable Security Boundaries (Phase 5.2)

To support enterprise-scale applications while maintaining DoS protection, the hardcoded bundle size limit is externalized.

| Feature | Specification |
|---------|---------------|
| **Configuration** | `max_bundle_size` in `pyproject.toml` |
| **Secure Default** | 256MB (enforced if unset or invalid) |
| **Atomic Validation** | Size check MUST occur before file memory mapping |

## 2.18 Security Invariants

The following security properties MUST be maintained to satisfy the Phase 5.0/5.2 Security Audit:

1. **Global Hash Coverage**: The `file_hash` field MUST cover the entire file volume (Header + Data). Bypassing the header (e.g., starting at offset 128) is a P0 security error.
2. **Boundary Validation**: `data_offset` MUST be validated against both `MIN_HEADER_SIZE` and the total physical file length.
3. **Deterministic Path Check**: Whitelisting MUST use a three-layer resolution protocol:
    - Layer 1: Raw Path match.
    - Layer 2: `read_link` target verification.
    - Layer 3: `fs::canonicalize` full resolution.
4. **Marshaling Depth Protection**: Python `marshal.loads()` MUST be executed within a temporarily reduced `sys.setrecursionlimit(500)` environment. Values > 500 are considered audit failures.
5. **Read Atomicity**: Large bundle reads MUST be protected via `flock(LockShared)` to prevent TOCTOU file replacement attacks during the verification-execution window.
